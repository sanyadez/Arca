# Arca

[English](README.md) · **Українська**

Зашифровані резервні копії з дедуплікацією для хоумлабу — один self-hosted сервіс.
(*Arca* латиною — скриня для цінного і ковчег: *arca Noë*, Ноїв ковчег.)

Один бінарний файл, на Bun без залежностей. Arca знімає теки на своїй машині й на інших машинах по SSH,
шифрує їх, перш ніж вони кудись підуть, і кладе в сховище, яке бачить лише шифротекст. Агенти ШІ
працюють із нею через власний MCP-сервер: запустити бекап, переглянути копії, відновити.

**Стан:** рання розробка (0.x). Формат сховища й API ще можуть змінюватися.

## Питання й відповіді

**Що вона робить?**
Ви перелічуєте теки, які треба берегти, — конфіги, дані застосунків, документи — і коли їх бекапити. Arca ріже
кожен файл на шматки за вмістом, зберігає кожен унікальний шматок один раз, шифрує й пише в репозиторій:
на локальний диск або на SFTP-сервер. Наступний знімок дописує лише змінене. Старі знімки проріджує політика
ротації (лишати 7 щоденних, 4 щотижневих, 12 щомісячних…), непотрібні дані прибирає prune, а репозиторій
регулярно перевіряється: частину його завантажують і розшифровують.

**Альтернативою чому вона є?**
restic, BorgBackup і Kopia — ідея та сама: шматки за вмістом, дедуплікація, шифрування на клієнті. Arca —
не кращий restic. Це один сервіс на весь хоумлаб: розклад, історія запусків, джерела на інших машинах і
HTTP API вбудовані, а не скрипти навколо CLI, а MCP-сервер дає агентам ШІ (Claude Code та іншим) працювати
з бекапами напряму. Формат репозиторію власний, не restic.

**У кого ключі?**
У вас. У кожного репозиторію свій випадковий головний ключ, який зберігається лише обгорнутим вашим паролем
(scrypt). Дані, назви файлів і структура тек шифруються AES-256-GCM ще до сховища. Ідентифікатори шматків —
хеші з ключем, тож сховище не може навіть перевірити, чи лежить у ньому відомий йому файл.
**Втрачений пароль не відновити**, а з ним і дані.

**Чи треба щось ставити на інші машини?**
Агента — ні. Сервер під'єднується по SSH і питає дві речі: стан усіх файлів (один `find`) і вміст змінених
(один потік `tar`). На машині потрібні OpenSSH, GNU find і GNU tar — тобто звичайний Debian чи Ubuntu. Ключ
можна прив'язати до примусової команди, яка дозволяє лише читати вибрані теки:
[docs/ssh-sources.md](docs/ssh-sources.md). Невеликий клієнт для машин, до яких сервер не дотягнеться, — у планах.

**А якщо самого сервера вже нема?**
`arca-restore` — окремий бінарник у кожному релізі. Дайте йому адресу репозиторію й пароль, і він покаже
знімки та відновить їх без сервера, конфігу й бази. Він лише читає сховище, тож підійде й копія репозиторію на
диску тільки для читання. Тримайте його копію й пароль окремо від сервера. Формат описано в
[FORMAT.md](FORMAT.md), тож дані можна прочитати навіть без Arca.

**Що отримують агенти?**
MCP-сервер (Streamable HTTP) з інструментами: перелік джерел і знімків, перегляд знімка, запуск бекапу чи
перевірки, відновлення в нову теку на сервері. Доступ — токенами з правами read, backup, restore, admin, тож
агентові можна дозволити бекапити й дивитися, але не prune і не відновлення.

**Чому така назва?**
Скриня тримає цінне зачиненим, ковчег проносить важливе крізь потоп: дані лежать зашифрованими, і їх можна
відновити, навіть коли від сервера нічого не лишилось. Слово однаково читається й вимовляється багатьма мовами
(воно є в іспанській, італійській, португальській) і коротке в командному рядку: `arca backup`, `arca-restore`.

## Стан

Уже працює:

- Знімки тек з виключеннями; повторний знімок читає лише змінені файли (розмір, mtime, inode).
- Дедуплікація шматками за вмістом (FastCDC) між файлами й знімками; стиснення zstd.
- AES-256-GCM, окремий ключ на кожен репозиторій під паролем (scrypt); кілька паролів на репозиторій.
- Сховища: локальна тека, SFTP (через системний OpenSSH).
- Джерела: локальні теки й теки інших машин по SSH, за бажання — з примусовою командою.
- Відновлення всього знімка чи його частини в нову теку; наявні файли ніколи не перезаписуються.
- Ротація (`forget`), збирання сміття (`prune`), перевірка цілісності (`check --read-data`), замки репозиторію.
- Сервер: розклад, ротація після кожного бекапу, prune і check за розкладом, історія запусків, HTTP API з токенами.
- MCP для агентів.
- `arca-restore`: відновлення без сервера.

У планах: S3 та інші хмарні сховища, кілька сховищ на джерело, дампи баз даних, сповіщення, кілька користувачів,
веб-інтерфейс, клієнт для віддалених машин.

## Встановлення

Реліз — це `arca-<версія>-<ціль>.tar.gz` (бінарники `arca` і `arca-restore`, приклад конфігу, systemd-юніт і
скрипт примусової команди для SSH), плюс `arca-restore-<версія>-<ціль>` окремим файлом і `SHA256SUMS`.
Цілі: `linux-x64`, `linux-arm64`. Bun не потрібен.

```sh
sha256sum --ignore-missing -c SHA256SUMS
tar xzf arca-<версія>-linux-x64.tar.gz
arca-<версія>-linux-x64/arca --version
```

Сервер: покладіть конфіг за зразком [config.example.json](config.example.json) у `/etc/arca/config.json`,
створіть токен `arca token <назва>` (він виведе рядок для конфігу), далі `arca serve /etc/arca/config.json`
або встановіть `arca.service` (він чекає бінарник у `/opt/arca/current/`).

## Команди

```sh
export ARCA_REPO=sftp://arca@192.0.2.30/data/repo
export ARCA_PASSWORD_FILE=~/.config/arca/repo.pass

arca init
arca backup /srv/data --exclude node_modules/ --exclude '*.log'
arca backup ssh://arca-src@192.0.2.20/etc/nginx --ssh-forced -i /etc/arca/source_ed25519
arca snapshots
arca ls latest -r
arca restore latest --target /tmp/restored --path docs
arca forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune
arca check --read-data --subset 0.1
```

Без сервера:

```sh
arca-restore snapshots --repo sftp://arca@192.0.2.30/data/repo
arca-restore restore latest --source web-data --target /tmp/restored
```

Усе перелічують `arca --help` і `arca-restore --help`.
